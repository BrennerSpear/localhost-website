Own Your Everyday AI

Make a tool you can run, change and keep using. Improve something that already exists; you don't need to recreate an entire app.

What should win

A useful tool someone can run, understand or adapt themselves: better dictation, local meeting notes, a home interaction or a creative instrument.

Sponsor

Variant

Choose the tools that work for your project.
Start small // Project seeds

Dictation that gets your names right

Extend an offline dictation app with a ten-term correction list, raw-versus-corrected preview and a way to add a term.

Demo: Read a short script before and after. Let a visitor add a term and try again offline. Start with Handy.

A recording becomes useful local notes

Import audio, transcribe locally, and draft decisions and action items linked to transcript passages. Save editable files in an ordinary folder.

Demo: Open the passage behind a decision, correct the note and reopen the file with networking disabled. Start with FluidAudio (supported Apple hardware) + a local model.

Two more directions +
  • One useful voice control for your home. Add one interaction to a prepared Home Assistant setup: a desk light, timer or virtual switch. Display what it heard and what it did.
  • A creative instrument powered by a local model. Put three useful controls over one working local image workflow. Save outputs with the settings needed to reproduce them.

For a local-only claim, show a prepared offline run. Set up models and hardware before the day; a prerecorded input or virtual device is a useful first version.

02

An Agent That Knows You

Make remembered context useful, understandable and controllable.

What should win

Useful memory that survives a new session, moves between agents, or can be inspected and corrected by its user.

Built with

Cognee

Connect your agents to the same memory backend and dataset. Test a fresh-session handoff before building the rest.
Start small // Project seeds

Pick up where your other agent left off

Connect two existing agents to one memory service. Store five approved facts, one decision with its reason and one next step. Add a “resume this project” command.

Demo: Teach agent A why a feature was postponed. A fresh session in agent B recalls the reason and source.

Fix what your agent remembers

Build a memory inbox with three controls: approve, show source and replace. Keep one fact per item and a simple source ledger.

Demo: Change a seeded morning-meeting preference to afternoons; fresh retrieval uses the correction.

Two more directions +
  • What did we decide, and why? Ingest three sample meeting notes. Answer with dated source excerpts, distinguish proposals from decisions and flag conflicting evidence.
  • An assistant that remembers your device's quirks. Combine one manual excerpt with three approved troubleshooting notes. Recall the earlier fix and cite its source. Keep recommendations read-only.

Shared memory needs the same backend and intentional dataset access; separate installations do not automatically share state. Removing or replacing a memory does not erase source files, prior transcripts or every cached copy. Cognee MCP ↗

Keep It Private

Build a hosted service that can work on sensitive inputs without giving its operator access to them.

What should win

A useful application with a verifiable boundary around its own processing as well as model inference. Show who can read the inputs and what the service releases.

Built with

Tinfoil

Run your parser, rules and output policy in a measured Container. Use a client that verifies the service before sending data.
Start small // Project seeds

Get help with a bug without handing over raw logs

Build diagnostic intake for a maintainer whose users need help but cannot share a full log. Inside a Tinfoil Container, parse one log format, apply secret-detection rules and use verified inference to explain the failure. Return a report, supporting excerpts and a redaction diff for the user to inspect before sharing.

Demo: Diagnose a seeded error in a synthetic log while excluding its fake API token from the report. Show the user choosing what to release. Show verification fail before upload when the client expects a different release.

Run a sealed evaluation with a verifiable result

A test owner and model builder want a score without exposing held-out examples to the service operator. Put a fixed scorer and restricted output policy in a measured Container. Start with one model and ten synthetic examples. Build a way for the relying party to verify that the result came from the agreed harness, model and test batch.

Advanced: Verify the result's origin and binding; a JSON score and version label alone are insufficient. Export only the agreed result, reject a mismatched workload and explain what even an aggregate score could reveal.

Prepare a CPU Container and verified client connection before hacking. Send inputs directly to the attested service, keep raw logs in memory only for the current request, limit outbound connections, and let users review exports. Verification does not establish model correctness or perfect redaction. Container setup ↗ · Verified connections ↗ · Evaluation example ↗

04

Build on Shared Compute

Make the community's Macs useful to one another. Help people find a peer who knows their setup or borrow inference from a friend's spare machine.

What should win

A useful contribution to Darkbloom's provider community: better peer support or inference sharing across independently owned machines.

Built with

Darkbloom

Work with the provider runtime and community's actual needs. Owner-only routing already exists; a cross-account lending gateway is something you build.
Start small // Project seeds

Find someone who has solved your Mac's problem

Build an opt-in peer directory with multiple machines per person, chip and memory details, model experience and a “happy to help” control. Let a member ask for help with a specific setup and find a relevant volunteer. Basic searchable hardware fields already fit in Slack profiles; add the multi-machine and peer-help workflow.

Demo: Find a willing peer for a model-loading problem on a particular Mac, then change their availability or remove their listing. Keep hardware claims self-reported and hardware labels separate from temporary availability.

Lend inference to your circle

Prepare two separately owned Macs, models and a trusted network. Build a thin gateway over Darkbloom's direct inference endpoints with a member allowlist, request queue, quotas and an owner-controlled lending switch. Never fall back outside the chosen circle or share the owner's account credentials.

Advanced: Run a task on a friend's Mac, refuse an outsider, then let the owner withdraw. A later request must fail or queue explicitly; accepted work must finish or cancel. Use public inputs—the host can read inference plaintext.

Darkbloom's self-route uses machines belonging to one account; it does not provide the cross-account group policy above. Direct endpoints need a trusted network plus gateway access controls. Keep hardware profiles opt-in and never collect private provider credentials. Direct endpoints ↗ · Owner routing ↗ · Slack profile fields ↗

Judging

Three common questions, with each sponsor adding its specific integration requirement. A small useful improvement can beat an unfinished general agent.

01 // Working

Does it work on a real task?

Show the workflow and its output. Let someone other than the builder try the intended task.

02 // Useful

Would someone keep using it?

Show the person you built for and the task they can now finish.

03 // Yours

What control does the user gain?

Explain where execution and data live, what dependencies remain, and what users can inspect, change or take with them.

A short submission card

What it does. What runs where. What data leaves. What was built today. How someone else can try it. Demonstrate your strongest privacy or control claim.
